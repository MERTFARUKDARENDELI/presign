# Presign browser extension

Reviews Solana signing requests on any website **before your wallet opens** — every request made through the wallet APIs it wraps (Wallet Standard and injected providers); while protection is on, anything it cannot review is refused. No link to share: when a site asks your wallet to sign, Presign opens its review, and the wallet is asked only after your decision. Presign advises; you decide.

## Install (developer mode)

```bash
npm run build:extension
```

Chrome / Edge / Brave → `chrome://extensions` → enable **Developer mode** → **Load unpacked** → select `extension/dist`.

The toolbar menu turns protection on or off, turns it off for the current site, picks the Presign instance (production picks mainnet or devnet by the request's chain), and lists recent decisions. A development build (`npm run build:extension:dev`) also offers "local" (`http://localhost:3000`); the production build does not list localhost in `externally_connectable` and never sends a review there, since any other local project could be listening on that port.

## How it works

```text
site ── signTransaction / signMessage / signIn ──▶ page hook (MAIN world, document_start)
page hook ── secret-named DOM events (secret handed over in a closed shadow root) ──▶ content script ──▶ background service worker
background ── opens ──▶ Presign /extension/review?rid=…&ext=…   (popup window)
review page: decode · simulate · deterministic rules · your decision · server approval
review page ── externally_connectable ──▶ background ──▶ content script ──▶ page hook
page hook ── the reviewed copy of the request ──▶ wallet ── signature ──▶ checked ──▶ site
```

- **What is wrapped:** Wallet Standard wallets (the `register-wallet` / `app-ready` handshake is intercepted, so the site only gets wrapped wallets; wallets that register through the legacy `window.navigator.wallets` list are routed through the same handshake, and the list cannot be replaced afterwards — apps that try log "window.navigator.wallets could not be set" and keep the wrapped wallets) and injected providers (`window.phantom.solana`, `window.solana`, `window.solflare`, `window.backpack`, …) — sign transaction(s), sign and send (one or several), sign message, off-chain message, Sign-In With Solana. **Default deny:** any other Solana signing feature, `sign…` provider method or `request({ method: "sign…" })` Presign cannot read is refused (or reviewed as unreadable), never passed through.
- **Same review as everywhere:** `/extension/review` uses the same analysis, decision rules and server approval as the rest of Presign. The requesting site is the origin the browser reports to the extension, not what the site claims.
- **Exact bytes, both ways:** the bytes are copied the moment the site calls, and after approval the wallet gets that copy — never the site's own array, which the site could change while you read the review. Injected providers take a transaction object: the wallet gets a view of it whose serialization is fixed to the reviewed bytes, and the site gets its own object back. When the wallet returns, a signed transaction may differ from the reviewed one only in its signature slots, and a signed message must be byte-identical with a signature that is valid for the reviewed bytes and account — otherwise the signature is withheld from the site. Signatures are checked with the browser's own Web Crypto (Ed25519); on plain-HTTP pages, or in a browser without Ed25519, only the bytes are compared.
- **Fails closed:** with protection on, a request Presign cannot review as sent (too large, more than 50 signatures at once, malformed) opens the review as unreadable, where Cancel is the only choice; if the review cannot open at all, or the extension was reloaded, the request is refused. Only the toolbar's own switches (protection off, or off for this site) let requests through unreviewed.
- **A page cannot rewire the hook:** the hook runs in the site's own JavaScript world, where the site can replace any built-in after the hook loaded. Everything from the site's call to the wallet's — copying the bytes, encoding the review request, the channel, waiting for and acting on the decision, calling the wallet — uses only built-ins captured at document_start (`lib/primordials.ts`), index loops, records without a prototype and typed-array indexing: never `btoa`, `Map` / `Set` / `Array` / `Promise` methods, `Function.prototype.call` / `bind`, the global `Promise` or `Proxy`, `await`, or a getter, setter or `then` a site added to `Object.prototype`. Fields of the site's objects are read once and pinned, so an accessor cannot show Presign one request and the wallet another. The wallet the site receives exposes only the six Wallet Standard properties (not the real wallet's descriptors, prototype or internal fields), and a `standard:events` change hands the app wrapped features.
- **Ownership once per session:** Presign approves only for a wallet you proved is yours (a message that authorizes nothing). Your wallet extension works on the review page too.
- **Channel to the extension:** the page hook keeps a random secret in a closed shadow root, which page scripts cannot open; the content script reads it with `chrome.dom.openOrClosedShadowRoot` at start-up and answers with an event named with it. No event ever carries the secret, so a site that fires the handshake events learns nothing, and the element is gone once the handshake is done (both checked in the Chrome end-to-end test). Messages then travel as DOM events named with that secret, built and dispatched with functions captured before the site could replace them and called through `Reflect.apply` — never `fn.call(…)`, since a site that replaced `Function.prototype.call` would receive the event and the secret in its name. The message text is built without `JSON.stringify` on an object, which would call a `toJSON` a site added. Review ids are random (Web Crypto, captured) and unique: a second review under a pending id is refused.
- **Approvals are confirmed, not trusted:** a message from the Presign review page proves only which page sent it. Before anything goes to the wallet, the background computes the payload hash from the bytes it captured itself and asks the Presign server the review was opened on (`POST /api/presign/signing/verify-approval`) whether its sealed approval is genuine, unexpired, for exactly that hash and type, and not confirmed before. Anything else — no answer included — blocks the request. The confirmed hash then travels with the decision to the page hook, which makes the last check itself: right before the wallet call it hashes what the wallet is about to receive, read from the very arguments the wallet gets (SHA-256, implemented in the hook: Web Crypto is asynchronous and absent on plain-HTTP pages), and sends nothing if it differs or if the approval carries no confirmed hash. Only the toolbar's own pass (protection off, or off for this site) goes without one.
- **No keys; one kind of request:** the extension never signs and never holds keys. Its only request is that confirmation, only to an allowed Presign origin, without cookies and without following redirects (`host_permissions` lists just the Presign origins; `tests/security/no-server-signing.test.ts` fails on any other request).

## Verified

- Unit tests: `tests/extension/*` (Wallet Standard interception with faithful event classes and a class-based wallet, injected providers, tampering wallets, batches, sign-in, re-entrancy, background decisions), `tests/security/presign-extension.test.ts` (decision path and page ↔ extension bridge).
- A hostile page: `tests/extension/hostile-page.test.ts` installs the hook, then replaces built-ins the way a site script can (36 replacements: Map / Set / WeakMap / WeakSet methods, `btoa`, `String.fromCharCode`, typed-array copies and `length`, Array methods and iterators, index and field accessors on `Array.prototype` / `Object.prototype`, `Object.prototype.then` / `toJSON`, `Promise.prototype.then` / `constructor`, the global `Promise`, `Function.prototype.call` / `apply` / `bind`, `Reflect`, `JSON`, `TextEncoder`, String and RegExp methods, `Object.keys` and descriptors, event methods, `CustomEvent`, `Proxy`, proxy traps on `Object.prototype` — each alone and all at once), then calls all 17 signing entry points with the user cancelling and approving through the real channel: cancel never reaches the wallet, approval signs exactly the reviewed bytes, which are the site's, and neither the secret nor an unwrapped wallet reaches the page. Against the previous hook, 36 of its 44 tests fail (42 with the check for the wallet's internal fields).
- The last check before the wallet: `tests/extension/payload-integrity.test.ts` — an approval confirmed for other bytes, one without a confirmed hash, a malformed hash, or one wrong hash in a batch never reaches the wallet (4 of its 6 tests fail with the check switched off); `tests/extension/sha256.test.ts` checks the hook's SHA-256 against Node's at every padding boundary.
- Real Chrome, end to end: `node scripts/extension-e2e.mjs` loads the built extension (`npm run build:extension:dev` for a local Presign) in a fresh profile, serves a test dApp with a fake Wallet Standard wallet and drives the review on a local Presign: a page script that pokes the handshake hears no secret; the wallet is not asked before the review; approve signs exactly the reviewed bytes, after the Presign server confirmed the approval; cancel and closing the window never reach the wallet; a CRITICAL request can be signed only after the explicit confirmation; a made-up approval sent from the Presign page is refused and never reaches the wallet; ownership is asked once per session; and after the page replaces `Function.prototype.call` / `apply`, `Promise.prototype.then` / `constructor`, `Object.prototype.then` / `toJSON`, `Map.prototype.set` / `has`, typed-array copies and `dispatchEvent`, the wallet is still not asked before the review, cancel still never reaches it, Presign reviews and the wallet signs exactly the site's bytes, and no event carrying the secret reaches the page (38/38 checks; the previous build fails 5 of them).

## Limits

- Presign's hook does not depend on any built-in a site can replace, but it cannot control the wallet's own page code. A site written for a particular wallet can still reach it around Presign (through the wallet's internals or its messages to its own extension), or change what that wallet's page code passes on. The wallet's own confirmation window stays the final check; only wallet-level integration closes this.
- Once the wallet has signed, its result passes through the wallet's own code before Presign's after-signing checks, so withholding a signature from a hostile site is best effort. What Presign guarantees is the order and the input: the wallet is asked only after your decision, with exactly the bytes you reviewed.
- `signAndSendTransaction` is broadcast by the wallet itself, so only what goes to the wallet can be checked (it is the reviewed copy).
- Injected providers: a wallet that rebuilds a transaction from the object's fields instead of serializing it would not be held to the reviewed bytes by the sealed view. Wallet Standard wallets receive bytes and are not affected.
- An injected wallet can lock a signing method against replacement (not writable, not configurable). Presign cannot wrap such a method; it says so in the toolbar menu's log ("NOT PROTECTED", with the wallet and method) instead of leaving it silently unreviewed.
- A Sign-In With Solana request whose account is chosen inside the wallet cannot be reconstructed in advance, so for it the order is reversed: the wallet signs first, Presign rebuilds the text for the account the wallet returned, requires the wallet to have signed exactly that (signature checked), and reviews it. The site receives the signature only if you continue; Cancel, a failed review or any mismatch withholds it. The wallet window therefore opens before Presign's review for this one case.
- Each transaction of a batch is reviewed separately; there is no combined view.
- Not yet published to the Chrome Web Store; not yet exercised with a real wallet extension (Phantom, Solflare, Backpack) — the end-to-end test uses a fake wallet. Wallets that add instructions to a transaction (priority fees, guard instructions) will have their signature withheld, by design; this needs checking against real wallets.
- The page hook is tested against hostile sites in unit tests (bytes swapped after the call, objects that serialize differently, oversized requests, unwrapped features); the Chrome end-to-end test covers an honest site, a page script probing the handshake, and a made-up approval.
